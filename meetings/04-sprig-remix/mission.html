Essential question

How can we change a working game without losing the rule that makes it fun?

  1. Play before you editFind the game’s promise.

    Open Sprig from the panel. Run the starter and play until you can explain the goal to a teammate.

    DoRun the game, try each control, and reach or miss the goal.
    You should seeA playable character, a map, an obstacle or goal, and a response when you win.

    Turn and talk

    What does the player try to accomplish? Which visual clue tells you where to go?

  2. Use the code compassFind the part you want to remix.

    Open the backup file in the Codespace tab for a map of the code. Sprig’s editor is where you run and save; the repository is where your team keeps a backup.

    setLegendart 
    [player, bitmap`...`]

    Defines how a symbol looks.

    setMapworld 
    setMap(map`...`)

    Places symbols into a level.

    onInputcontrol 
    onInput("d", () => ...)

    Responds to a player input.

    Which function controls where the player and goal are placed?

  3. Make the guided remixRun after each small change.

    In Sprig, change one thing, press Run, and compare the result with your prediction.

    EDIT 1 · Player art

    Change one color or pixel in the player bitmap. Keep the same symbol key.

    [player, bitmap`... one pixel changed ...`]

    EDIT 2 · Map tile

    Move the goal or add a wall in the map. Keep a path that a new player can discover.

    setMap(map`wwwww / w p g / wwwww`)

    EDIT 3 · Theme

    Rename the game in your instructions and choose a visual theme for the art.

    Theme: “Museum of Lost Buttons”

    Beginner finish line: the art and map changed, the game still runs, and the goal is still possible. Behavior changes are optional Builder work.

  4. Playtest the remixLet another player discover the rules.

    Complete the guided baseline first

    Remix

    Change art, map, theme, and instructions.

    Builder

    Add a second level, obstacle, sound, or starting position.

    Boss

    Change a rule and explain how the input handler or win condition works.

    Player test

    1. Give the controls to a player without explaining the map.
    2. Ask what they think the goal is.
    3. Record one thing they understood and one thing to clarify.
  5. Save, back up, and explainKeep the experiment recoverable.

    Save in Sprig, copy the final code into the backup file, and commit with Meeting 4: Sprig remix. Sync, verify, and stop the Codespace.

    Demo sentence: “We changed ____ so the game feels like ____. We preserved ____ so players can still ____.”

    Stuck ladder

    1. Run the last working version again.
    2. Compare one changed bitmap or map row with the starter.
    3. Restore the backup file if the editor is damaged.
    4. Ask a teammate, teacher, or optional AI adviser about one specific function.

Build together

Playtesting is a design role.

One person can make the edit while three people notice, predict, and test.

Driver

Copies one safe change and runs it.

Navigator

Maps symbols, controls, and the goal.

Designer / tester

Checks whether the theme and goal read clearly.

Documentarian

Backs up the code and records the test.

Ready to leave?

A game someone else can play is the finish line.

Keep the backup code safe; the best remix is the one you can recover.
